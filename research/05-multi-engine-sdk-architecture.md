## The headline

> **Every multi-platform vendor examined avoids hand-maintaining N copies of the same logic — but not
> one of them does it the way SoulEngine does.** What gets shared or generated is always an **API
> surface**, a **type contract**, or a **native binary core**. Nobody was found code-generating or
> sharing *behavioural simulation logic* across engines.

SoulEngine currently hand-maintains cognition twice (TypeScript and C#), and Option B extends that to
three or four with Unreal and Godot. That specific pattern has **no industry precedent** in this
evidence set.

## What the vendors actually do

### PlayFab — one spec, one generator, every SDK emitted `high`

> "This is a node.js based program that takes a json description of the PlayFab API and uses it to
> generate out all the different SDKs." — `SDKGenerator` README

Microsoft Learn is blunter: the generator *"contains the sources for all PlayFab SDKs on all platforms.
**If you want to make a change in an SDK, this is where the change has to go.**"*

Mechanically corroborated: `UnitySDK`, `CSharpSDK`, `JavaScriptSDK`, `NodeSDK` and
`UnrealMarketplacePlugin` each carry a top-level `genConfig.json`. The spec itself lives in a **separate
versioned repo** (`PlayFab/API_Specs`, 777 commits) whose README says it is automatically populated and
that manual edits get overwritten — the spec is machine-published *upstream* of the generator, and is
consumable from a local clone, GitHub raw, or the live API server.

**The Unreal plugin is generated, not hand-ported.** `PlayFabClientAPI.h` opens: *"// Automatically
generated header file for the UE4 PlayFab plugin."* The repo ships **thirteen full plugin copies**, one
per Unreal version (4.23–4.27, 5.0–5.7) — *tractable only because it is machine-emitted*.

One CI pipeline stamps everything: Unreal `1.192.260805` / `adobuild_unrealmarketplaceplugin_281`,
CSharpSDK `1.229.260805` / `adobuild_csharpsdk_289` — identical date component, identical build-identifier
pattern, same release day.

*Caveat carried:* per-target templates, transport, editor plugin and examples are hand-maintained. The
generated portion is the **API surface**.

### RevenueCat — shared intermediary over two native cores `high`

> "The hybrid SDKs themselves are fairly simple message-passing interfaces."

> "Rather than immediately pass from a hybrid SDK to, say, our Android SDK, we've created an intermediary
> wrapper library called **purchases-hybrid-common**."

Every hybrid wrapper (Flutter, React Native, Cordova, **Unity**) sits on that one shared layer, which in
turn depends on the native iOS and Android SDKs.

**Their anti-drift mechanism is process, not tests** — a scheduled release train with a deliberate stagger:

> "Every Wednesday at 17:00 UTC, a new pipeline is triggered in CircleCI" … "Every Monday … a new pull
> request is opened, updating purchases-hybrid-common to depend on the latest purchases-android and
> purchases-ios."

The week-long stagger is intentional: *"to detect important bugs early and prevent them from making it to
the multi-platform SDKs."*

*Limits carried:* the shared layer sits **above two independently maintained native cores** (Swift and
Kotlin), so it de-duplicates binding and serialization, not core logic. The post is from 2022 (updated
2024) and names CircleCI, so tooling may have drifted. **No Unreal SDK exists in this train.**

### Steamworks.NET — headers as schema `high`

The entire `autogen/` C# surface is generated from Valve's C++ headers by `SteamworksParser` plus
`Steamworks.NET-CodeGen`. Generated files self-identify: *"// This file is automatically generated. //
Changes to this file will be reverted when you update Steamworks.NET."*

**And the counter-example matters:** the rival binding **Facepunch.Steamworks is an independent,
hand-written P/Invoke layer over the same SDK** — a live demonstration that when you skip the
shared-schema route, you get exactly the duplicate-maintenance situation SoulEngine is in.

## The finding that matters most `high`

> **"None of the verified evidence shows any vendor code-generating or sharing behavioural/simulation
> logic across engines — the shared artifact is always an API surface, a type contract, or a native
> binary."**

PlayFab's spec describes HTTP request/response DTOs and method stubs — *far* easier to codegen than
cognition. RevenueCat's shared layer is mapping and serialization over hand-maintained cores.
Steamworks.NET's generator targets exactly one language, so it prevents drift between C# and the native
SDK, **not between multiple engine ports**.

The pass states the implication directly:

> "The industry pattern that actually eliminates per-engine reimplementation is **a single native core
> behind a C ABI with generated thin bindings** (the Wwise/FMOD model, *not verified in this pass*), or
> **a service boundary with a generated client** (the PlayFab model) — not two hand-maintained
> behavioural copies."

## What this changes

| PRODUCT.md | Effect |
|---|---|
| `D6` multi-engine scope | **Answered, and the answer is uncomfortable.** Extending Option B to Unreal and Godot by reimplementing cognition per engine matches no vendor practice found. The two patterns that work are a native core behind a C ABI, or a service boundary with a generated client. |
| §3.3 **Option C** (thin client + server) | **Retroactively supported.** "A service boundary with a generated client" *is* Option C. This does not reopen `D2` — B is sound for Unity-only, which is the near-term product — but it means **the multi-engine story is the weak part of B, not the key handling.** |
| backlog **5.2** (TS↔C# conformance tests) | **Promoted from hygiene to load-bearing.** With no shareable core, fixtures are the only drift control available. RevenueCat's answer was *process* — a fixed release cadence — which is worth copying alongside the fixtures for a solo maintainer. |
| A third option worth costing before Unreal | Extract cognition into a **single core behind a stable ABI** (or a local service the engine plugin talks to) and generate or hand-write thin per-engine shells. That is the Wwise/FMOD shape, and it preserves Option B's "you host nothing" property while collapsing N runtimes to one. |

## STILL UNANSWERED — third consecutive failure

**Zero claims** on comparable-product pricing (Q5) or licence enforcement in game middleware (Q7). The
pass says so explicitly rather than inferring:

> "No pricing page (Convai, Inworld, Charisma.ai, ElevenLabs, Photon, PlayFab), no Unity Asset Store
> listing survey, no publisher post-mortem or revenue thread, and no middleware licensing documentation

Three attempts, three failures, and this time the search budget was *not* the stated cause. The likely
real cause is mechanical: pricing pages are JavaScript shells and bot-protected (Fab returned 403 to
automated fetches in Pass C1, and Charisma's page only yielded to a live fetch during verification).
