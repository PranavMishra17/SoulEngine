# Spec 5.9 — Conversation Replay and Evaluation Harness

**Status:** Implementation  
**Created:** 2026-09-05  
**Owner:** Backend / Cognition

---

## Problem

The NPC cognition layer has been rewritten twice based on impression, with no measurements. The current architecture runs Mind and Speaker in parallel: Speaker replies immediately while Mind reasons with tools in the background. Because they are parallel, memory-recall results arrive too late for the current reply and are deferred to the NEXT turn — so an NPC answers a memory question one turn late.

This feels wrong, but has never been measured. Industry research found no validated alternative architecture to copy. The only defensible path is to measure first. This harness makes a third rewrite judgeable instead of another guess.

## Solution

A deterministic, offline, zero-cost replay harness. No network. No real provider calls. No API keys required to run it.

## Components

### 1. Stub LLM Provider (`src/providers/llm/stub.ts`)

Implements the `LLMProvider` interface (`src/providers/llm/interface.ts`) with:
- Scripted responses from a fixture
- Tool call support
- Configurable artificial latency per call (for reproducible timing behavior)
- Deterministic streaming (no real network)

**Interface:**
```typescript
export interface StubLLMConfig {
  responses: StubResponse[];
  defaultLatencyMs?: number;
}

export interface StubResponse {
  text?: string;
  toolCalls?: ToolCall[];
  latencyMs?: number; // override default
}
```

### 2. Fixture Format (`tests/fixtures/conversations/`)

JSON files defining scripted conversations:

```typescript
export interface ConversationFixture {
  name: string;
  description: string;
  npc: {
    definition: NPCDefinition;
    instance: NPCInstance;
    knowledgeBase?: KnowledgeBase;
  };
  playerInfo?: PlayerInfo;
  turns: FixtureTurn[];
}

export interface FixtureTurn {
  playerInput: string;
  mindResponses: StubResponse[];
  speakerResponses: StubResponse[];
  expectations?: TurnExpectations;
}

export interface TurnExpectations {
  recallFacts?: string[];       // facts that SHOULD appear in reply or prompt
  toolsCalled?: string[];        // tool names that SHOULD be called
  toolsNotCalled?: string[];     // tool names that SHOULD NOT be called
}
```

**Validation:** Use zod schemas in `src/schema/eval.ts`, following existing patterns in `src/schema/index.ts`.

### 3. General-Purpose Stage Timer (`src/eval/timer.ts`)

Records named stages with millisecond offsets from a start point. Not voice-specific.

```typescript
export class StageTimer {
  markStart(): void;
  mark(stage: string): void;
  getStages(): Record<string, number>;
  hasStage(stage: string): boolean;
  elapsed(fromStage: string, toStage: string): number | null;
}
```

**Note:** `LatencyTracker` exists at `src/voice/pipeline.ts:97` but is voice-specific (commit → firstTranscript → firstToken → firstAudio). Do not contort it. Write a general one. Say in the completion report whether the voice one should later be refactored onto it.

### 4. Replay Runner (`src/eval/replay.ts`)

Runs a fixture end-to-end through the real cognition path with the stub provider substituted.

**Per-turn report:**
```typescript
export interface TurnReport {
  turn: number;
  playerInput: string;
  speakerResponse: string;
  timings: {
    mindDurationMs: number;
    speakerDurationMs: number;
    totalMs: number;
    stages: Record<string, number>; // from StageTimer
  };
  recall: {
    expectedFacts: string[];
    factsInReply: string[];
    factsInPrompt: string[];
    hitRate: number; // 0-1
  };
  tools: {
    expectedCalls: string[];
    actualCalls: string[];
    unexpectedCalls: string[];
    accuracy: number; // 0-1
  };
}

export interface ReplayReport {
  fixture: string;
  turns: TurnReport[];
  aggregate: {
    avgMindLatencyMs: number;
    avgSpeakerLatencyMs: number;
    avgTotalLatencyMs: number;
    recallHitRate: number;
    toolAccuracy: number;
  };
}
```

**Runner signature:**
```typescript
export async function runReplay(fixture: ConversationFixture): Promise<ReplayReport>;
```

### 5. Eval Script (`package.json`)

```json
{
  "scripts": {
```

Prints readable per-turn and aggregate tables. No emojis. Plain text.

### 6. Deferred-Recall Fixture (`tests/fixtures/conversations/deferred-recall.json`)

The most valuable artifact: a scripted conversation where the player states a fact, then asks about it on the very next turn. The expectation is recorded at the turn where a correct system would answer.

Whether it currently passes or fails, the harness must report it honestly and the result must be reproducible.

**Do NOT "fix" the deferred-recall behaviour in this item** — the job is to make it measurable, not to change it.

## Acceptance Criteria

1. Stub LLM provider implements `LLMProvider` interface, returns scripted responses, supports tools, and simulates configurable latency. Unit tests prove it honors its script and latency.
2. Fixture format is explicit and documented. Zod validation rejects malformed fixtures. Schema lives in `src/schema/eval.ts`.
3. Replay runner executes a fixture end-to-end through real cognition with stub provider, returns structured report with stage timings, recall correctness, tool correctness.
4. `npm run eval` prints readable per-turn and aggregate tables.
5. Deferred-recall fixture exists, runs, and reports actual measured numbers for the baseline behavior.
6. Running the same fixture twice yields identical recall and tool results (deterministic).

## Testing Strategy

Write tests FIRST:
- `tests/unit/stub-provider.test.ts` — stub honours script and latency
- `tests/unit/stage-timer.test.ts` — timer records and aggregates correctly
- `tests/unit/fixture-validation.test.ts` — zod rejects malformed fixtures
- `tests/e2e/replay-runner.test.ts` — runner executes fixture end-to-end, produces report with expected shape and non-zero timings
- `tests/unit/replay-determinism.test.ts` — running same fixture twice yields same recall and tool results

## Constraints

- Runs offline with no API keys and no network. If any test needs a key or socket, the design is wrong.
- Test code lives under `tests/`; harness source under `src/eval/` or `src/providers/llm/stub.ts`.
- Nothing in the runtime bundle should depend on test fixtures.
- Minimal changes to cognition implementation (`src/core/*`, `src/routes/conversation.ts`, `src/voice/pipeline.ts`) — only for dependency injection and observing timings. Document any forced changes.
- No emojis anywhere.
- Full `npm test` and `npm run typecheck` must be green with zero new failures.
