# 5.17 — Text harness for driving and validating NPCs

## Problem

There is no way to hold a real conversation with an NPC and see what its mind is doing.

The web playground is browser-driven and session-shaped: it shows dialogue, not internals, and it does
not survive across sessions in a way anyone inspects. The eval harness (`src/eval/`) is the opposite —
deterministic, stubbed, scripted — and answers "did this regress", never "does this work".

So the marquee features have never been observed working:

- **Cycles have never run outside an explicit HTTP call.** `runDailyPulse`, `runWeeklyWhisper` and
  `runPersonaShift` are invoked from exactly one place, `src/routes/cycles.ts`. Nothing schedules them.
  Short-term memories accumulate at session end and are promoted to long-term memory only if a human
  remembers to POST an endpoint. The five pillars are untested end to end.
- **Cross-session recall is unmeasured.** `tests/fixtures/conversations/deferred-recall.json` records
  0% same-turn recall. Whether a fact survives to a *later session* is unknown.
- **Knowledge tiers and tool affordances are invisible.** Nothing shows which knowledge depth tiers an
  NPC could reach versus which were injected, or which tools it was permitted to call versus which it
  chose.

## Goal

A text-only CLI that an agent (or a person) drives turn by turn, against the real NPCs in a real
project, with the NPC's internal state and affordances printed alongside every reply — so that
validating a feature means reading a diagnostic block, not inferring from dialogue.

Explicitly **not** a scenario language, a simulated player, or a judge model. The driver improvises;
the harness observes and records.

## Design

### Shape

`npm run npc -- <command>`, implemented in `src/harness/`. In-process: it calls `src/core/*` and the
storage layer directly. No HTTP server to run, and it can surface state the API deliberately hides.

Each invocation is one turn. Harness state (active session, transcript, turn count) persists to disk
between invocations so a conversation survives across separate command calls and across sessions.
That persistence is the feature — it is what makes "does it remember me four sessions later"
answerable at all.

### Commands

| Command | Behaviour |
|---|---|
| `world [--project <id>]` | Projects, NPCs, which have live instances, active session if any |
| `talk <npcId> "<text>"` | One turn. Prints reply plus the diagnostic block below |
| `inspect <npcId>` | Full mind state: core anchor, mood, STM, LTM, trait modifiers, relationships |
| `affordances <npcId>` | What this mind can reach: knowledge tiers and callable tools (below) |
| `endsession` | Ends the active session through the production path, creating STM |
| `cycle daily\|weekly\|persona <npcId>` | Runs the cycle and prints a before/after diff |
| `seed fishing\|office\|space` | Creates a scratch project from a starter pack, for multi-NPC work |
| `reset <npcId>` | Instance state back to fresh |
| `log [--last N]` | Replays recorded turns and telemetry for review |

### The diagnostic block

Printed after every `talk`. This is what separates a validation tool from a chat toy.

```
--- turn 7 | npc_mjxqkqbn (Aria) | session sess_... ---
reply     : "..."
mind      : tools called   recall_memories(query="books") -> 2 hits
            tools offered  recall_npc, recall_knowledge, recall_memories, exit_convo,
                           lock_door, call_guards            (6 offered / 1 called)
            denied         flee_to  (not in mcp_permissions)
knowledge : world/1-2 injected (2 of 3 tiers granted; tier 3 exists but not granted)
            lore/1 injected  (1 of 1)
            ~410 chars injected, budget 2000
recall    : deferred context from turn 6 injected: YES (2 facts)
            this turn's recall deferred to turn 8
memory    : STM 4 -> 5   LTM 2 -> 2
mood      : cautious (0.4) -> guarded (0.3)
timing    : mind 812ms | speaker 640ms | wall 858ms
```

Three things it must make legible, per the brief:

1. **Knowledge tiers as prescribed.** For each category: tiers that exist (`getAvailableDepths`), tiers
   this NPC is granted (`knowledge_access`), tiers actually injected (`resolveCategoryKnowledge`), and
   the character cost against the token budget. A granted-but-not-injected tier is a bug worth seeing.
2. **Available function calls, not just fired ones.** What the Mind was offered
   (`getMindAvailableTools`, `getAvailableTools`, `getGameEventTools`), what it called, and what was
   withheld by `hasToolPermission`. A mind that never calls a tool it was never offered is a
   configuration problem, not a model problem, and today those look identical.
3. **The deferred-recall seam.** Whether the previous turn's mind context was injected into this turn's
   speaker prompt, and that this turn's recall is deferred to the next. This is the known 0% path;
   making it visible per turn is how its behaviour across sessions gets established.

### Telemetry and logs

Every turn appends a structured record to a per-run JSONL file under the harness state directory:
turn index, npc, session, the diagnostic fields above, token usage, and stage timings. `log` renders
it back as text.

Two consumers: me, reading it during a session; and later analysis, since a JSONL of real turns is
exactly the input a future evaluation would want. It reuses the stage timer from `src/eval/timer.ts`
so there is one timing vocabulary, not two.

### Providers

Real by default, reading the project's stored key through the existing secrets path. `--stub` uses the
deterministic provider from `src/providers/llm/stub.ts` for free smoke runs.

**Known risk:** the BLAST project carries `secrets.enc.undecryptable.bak` beside its `secrets.enc`,
which suggests a past encryption-key rotation. If the stored key does not decrypt under the current
`ENCRYPTION_KEY`, real mode must fail with a message that says exactly that and names `seed` and
`--stub` as the ways forward — not a stack trace.

### Limits

A turn cap per session, default 50, configurable. It stops a runaway loop from spending real tokens.

## Acceptance criteria

1. `world` lists the real projects and NPCs from local storage, including BLAST.
2. `talk` holds a genuine multi-turn conversation: state persists across separate process invocations,
   proven by two consecutive commands where the second refers to the first.
3. Every `talk` prints the diagnostic block, including tiers offered-vs-injected and tools
   offered-vs-called-vs-denied.
4. `endsession` creates STM through the same path production uses.
5. `cycle weekly` prints an STM/LTM before-after diff, making promotion observable.
6. `seed office` produces a project with multiple NPCs that `talk` can address by id.
7. `--stub` runs the whole loop with no network and no API key.
8. Turn cap stops a session and says so.
9. A run writes JSONL telemetry that `log` renders back.

## Test plan

Harness tests run in **stub mode only** — no network, no keys — under `tests/`:

- `tests/unit/` — diagnostics assembly: given a definition with three knowledge tiers and access to two,
  the block reports `2 of 3`; given permissions withholding a tool, it appears under denied.
- `tests/unit/` — turn cap trips at its limit; telemetry records round-trip through `log`.
- `tests/e2e/` — state persistence: two separate runner invocations continue one conversation, and the
  transcript proves the second saw the first.
- `tests/e2e/` — `endsession` creates STM; `cycle weekly` moves entries STM to LTM.

Real-provider behaviour is validated by using it, which is the point of the tool.

## Constraints

- **No changes to `src/core/*`.** If observing the mind requires modifying cognition, that is a finding
  to report, not a change to slip in. Where a diagnostic cannot be obtained without a core change, the
  spec records the gap instead.
- Harness source in `src/harness/`; tests in `tests/`; no test code in the shipped bundle.
- `CLAUDE.md` rules: no hardcoded secrets or magic strings, no emojis anywhere, graceful errors with
  logged context, DRY, minimal footprint.

## Out of scope

Scenario files, a simulated player, a judge model, and anything that schedules cycles automatically.
The scheduler is real missing work but belongs to backlog 5.4, not here.

## What this is expected to reveal

Recorded now so it can be checked against later: within-session recall is already measured at 0% on
the deferred path, cycles have never run outside a manual HTTP call, and the BLAST instance has almost
certainly never had a weekly whisper promote anything. If the first real session shows memory working
inside a session and failing across sessions, that is the prediction landing, not a surprise.
