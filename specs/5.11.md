# Spec 5.11 — Fix Replay Harness Parallel Turn Topology

**Status:** Implementation  
**Created:** 2026-09-05  
**Owner:** Backend / Cognition  
**Builds on:** [5.9](./5.9.md)

---

## Problem

The replay harness added in [5.9](./5.9.md) runs Mind and Speaker **sequentially**, but production (`src/routes/conversation.ts`) runs them **concurrently**. This makes the harness's latency measurements inaccurate.

The harness reports a total latency of `mind + speaker` (sequential sum), but production's actual wall-clock latency is approximately `max(mind, speaker)` (overlap). The harness exists specifically to compare cognition architectures by latency, so measuring a different topology than production defeats that purpose.

**Evidence:** Comment at `src/eval/replay.ts:118` explicitly states "in parallel with Speaker in real system, but sequential here for measurement", and the code awaits Mind before starting Speaker.

## Solution

Update `src/eval/replay.ts` to mirror production's parallel topology from `src/routes/conversation.ts`:

1. Start Mind in background (returns promise, does not block)
2. Stream Speaker immediately (runs while Mind executes)
3. Await Mind result after Speaker completes

The report already distinguishes stage durations (Mind, Speaker) from wall-clock total. The fix changes the implementation to match the production topology so the wall-clock measurement is accurate.

## Implementation

### Changes to `src/eval/replay.ts`

**Before (lines 113-163, sequential):**
```typescript
// Build conversation history
const llmHistory = assembleConversationHistory(conversationHistory, 20);

// Run Mind agent (sequential)
timer.mark('mind_start');
const mindResult = await runMindAgentLoop(...);
timer.mark('mind_end');

// Assemble Speaker prompt
let speakerPrompt = await assembleSlimSystemPrompt(...);
if (deferredMindContext) {
  speakerPrompt = augmentPromptWithMindContext(...);
}

timer.mark('speaker_start');
// Run Speaker
let speakerResponse = '';
for await (const chunk of speakerProvider.streamChat(...)) {
  if (chunk.text) speakerResponse += chunk.text;
}
timer.mark('speaker_end');
```

**After (parallel):**
```typescript
// Build conversation history
const llmHistory = assembleConversationHistory(conversationHistory, 20);

// Assemble Speaker prompt BEFORE starting concurrent execution
let speakerPrompt = await assembleSlimSystemPrompt(...);
if (deferredMindContext) {
  speakerPrompt = augmentPromptWithMindContext(...);
}

// Start both Mind and Speaker concurrently
timer.mark('mind_start');
timer.mark('speaker_start');

// Start Mind in background (does not block)
const mindPromise = runMindAgentLoop(...).then(result => {
  timer.mark('mind_end');
  return result;
});

// Stream Speaker immediately
let speakerResponse = '';
for await (const chunk of speakerProvider.streamChat(...)) {
  if (chunk.text) speakerResponse += chunk.text;
}
timer.mark('speaker_end');

// Await Mind result (likely already complete)
const mindResult = await mindPromise;
```

### Report Structure (unchanged)

The `TurnReport` interface already has the correct structure:

```typescript
timings: {
  mindDurationMs: number;      // Stage duration for Mind
  speakerDurationMs: number;   // Stage duration for Speaker
  totalMs: number;             // Wall-clock turn total (reflects overlap)
  stages: Record<string, number>;
}
```

The `totalMs` is measured from `player_input_added` to `turn_complete`, which captures the wall-clock time for the entire turn. No changes needed to the report structure — only the implementation to make Mind and Speaker run concurrently so `totalMs` reflects production topology.

## Refactoring Assessment

**Question:** Could turn orchestration be extracted into a shared function used by both `conversation.ts` and `replay.ts`?

**Answer:** Not in this item. The refactoring would touch ~70-80 lines across 3 files (new orchestration function + wrappers in both callers), compared to ~10 lines for the concurrency fix. The two paths have diverged:

- `conversation.ts`: per-project provider resolution, timeout/abort controller, MCP follow-up, token tracking, mood updates
- `replay.ts`: stub providers, no timeout, timing measurement, recall/tool correctness analysis

Forcing them into a shared function would require many optional parameters and callbacks, reducing clarity. The core pattern is shared (start Mind, stream Speaker, await Mind), but the surrounding concerns differ enough that extraction is not worth the complexity.
