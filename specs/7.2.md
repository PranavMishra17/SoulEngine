# 7.2 — Make the endpointing budget a project setting

Backlog row: 7.2 in [`backlog.md`](../backlog.md), Tier 7. Pass E immediate win
([`research/09-npc-runtime/PROPOSAL.md`](../research/09-npc-runtime/PROPOSAL.md) §3 item 1).

## Problem

Before the model generates a single token of a voice turn, three independent timers run to
completion:

- Deepgram `utterance_end_ms: 1000` and `endpointing: 500`, hard-coded at
  [`src/providers/stt/deepgram.ts:85-86`](../src/providers/stt/deepgram.ts)
- the client-side debounce `AGGREGATION_WINDOW_MS = 400`, a `static readonly` at
  [`src/voice/pipeline.ts:194`](../src/voice/pipeline.ts), armed at `pipeline.ts:439-454`

Worst case is ~1.4s, and the code's own comment says so. The few-and-deep target is a 1-2s turn;
production voice stacks report 400-800ms end to end
([`research/09-npc-runtime/a-voice-turn-pipelines.md`](../research/09-npc-runtime/a-voice-turn-pipelines.md)
§6). The endpointing chain alone consumes most of the budget, and none of the three numbers can be
changed without a code deploy, so they cannot be tuned per game, per language, or measured against
each other.

Deepgram's own model-based end-of-turn detection is a different API surface and is **not** this item; it
is tracked as 7.7 and depends on this one, because it needs the same configuration seam.

## Decisions

1. **Three settings, one place.** `ProjectConfigSchema`
   ([`src/schema/index.ts:185-194`](../src/schema/index.ts)) gains an optional
   `voice_latency` object: `{ utterance_end_ms?: number; endpointing_ms?: number;
   aggregation_window_ms?: number }`, each a positive integer, with the mirrored TypeScript type in
   `src/types/project.ts`. Defaults are the current values (1000 / 500 / 400) so existing projects
   behave identically.
2. **The STT contract carries them.** `STTSessionConfig`
   ([`src/providers/stt/interface.ts:17-28`](../src/providers/stt/interface.ts)) gains optional
   `utteranceEndMs?: number` and `endpointingMs?: number`. `DeepgramSession` reads them into the
   `listen.live` options at `deepgram.ts:70-88` in place of the literals, falling back to the defaults.
   The defaults live as named constants in `deepgram.ts`, not repeated in the pipeline.
3. **The pipeline reads its window from config.** `VoicePipelineConfig`
   ([`src/voice/pipeline.ts:58-75`](../src/voice/pipeline.ts)) gains optional
   `aggregationWindowMs?: number`; the `static readonly` becomes an instance field defaulting to 400.
   The pipeline also passes `utteranceEndMs` / `endpointingMs` through when it builds `sttConfig`
   (`pipeline.ts:~260-294`).
4. **The WebSocket handler threads the project values.** Where `ws/handler.ts` constructs the pipeline
   (`handler.ts:~537-577`) it reads `project.config.voice_latency` and passes the three values. If the
   project has none, nothing is passed and the defaults apply.
5. **One log line at session start** records the three effective values, so a live measurement can be
   attributed to a configuration. The budget comment at `pipeline.ts:180-188` is rewritten to describe
   the setting rather than the constant.
6. **Not in scope:** changing the defaults, Deepgram Flux or any end-of-turn model (7.7), exposing the
   settings in the studio UI (frontend worktree), the commit-path behaviour at `pipeline.ts:436-456`
   beyond reading the configurable window.

## Scope

Touch: `src/schema/index.ts`, `src/types/project.ts`, `src/providers/stt/interface.ts`,
`src/providers/stt/deepgram.ts`, `src/voice/pipeline.ts` (config field, window field, sttConfig build,
comment), `src/ws/handler.ts` (pass-through), and the fixture or default-project factory if one
validates `ProjectConfig` strictly.

Do not touch: TTS, LLM providers, `runConversationTurn`, transcript accumulation logic.

## Test plan

`tests/unit/voice-latency-config.test.ts`:
- `ProjectConfigSchema` accepts a config without `voice_latency` (existing fixtures parse unchanged).
- It accepts `{ utterance_end_ms: 600, endpointing_ms: 300, aggregation_window_ms: 150 }` and rejects
  `0`, negatives and non-integers.
- `VoicePipeline` constructed with `aggregationWindowMs: 50`: after a commit with pending text, the
  aggregated transcript is processed after ~50ms and before 400ms (fake timers; the existing pipeline
  unit tests show how the pipeline is constructed with stub providers).
- `VoicePipeline` constructed without the field: the window is 400.
- The STT session config handed to `sttProvider.createSession` carries `utteranceEndMs` and
  `endpointingMs` when the pipeline was given them, and omits them otherwise.

`tests/unit/deepgram-endpointing-options.test.ts`:
- With a mocked Deepgram client, `DeepgramSession.connect()` passes `utterance_end_ms: 600` and
  `endpointing: 300` when configured, and `1000` / `500` when not. Follow the mocking approach the
  existing Deepgram tests from backlog 4.4 use.

Existing voice tests stay green.
