# Spec 5.8 - Token-Vending Key Broker (Proxy Strategy)

## Context

The product is an NPC SDK for game developers. They bring their own OpenAI/Anthropic/Gemini/ElevenLabs/Deepgram keys (BYOK). Those keys MUST NOT ship inside a distributed game build:
- OpenAI explicitly prohibits it in their ToS
- Unity Asset Store Submission Guidelines forbid packages that "incorporate the key into project builds"

Industry answer: a broker service the game developer deploys that holds long-lived keys and issues short-lived scoped credentials to game clients.

## Design Constraint

The broker needs **two strategies behind one contract**:

1. **vend** - Provider has an ephemeral-credential API (OpenAI Realtime, ElevenLabs signed URLs, Deepgram temporary keys). Broker gets a short-lived provider credential and hands it to the client, which calls the provider directly.

2. **proxy** - Provider has NO ephemeral-credential API (Anthropic, Gemini, OpenAI chat completions). Broker must forward the request itself using the stored key.

This spec implements the `proxy` strategy for LLM only. The `vend` interface is defined but concrete implementations are deferred to a follow-up.

## Architecture

### Token Flow

```
Client                    Broker                    Provider
  |                         |                          |
  |-- x-api-key ----------->|                          |
  |<-- broker token --------|                          |
  |                         |                          |
  |-- broker token + req -->|                          |
  |                         |-- provider key + req -->|
  |                         |<-- completion -----------|
  |<-- completion ----------|                          |
```

### Modules

- `src/broker/token.ts` - Mint/verify HMAC-SHA256 signed tokens
- `src/broker/strategy.ts` - Interface for vend/proxy strategies
- `src/broker/middleware.ts` - `requireBrokerToken` validation
- `src/routes/broker.ts` - HTTP endpoints

### Token Structure

HMAC-SHA256 signed JWT-like payload:
```json
{
  "jti": "unique-token-id",
  "projectId": "project-123",
  "scopes": ["llm"],
  "iat": 1234567890,
  "exp": 1234568790
}
```

Signature key: sourced from `BROKER_TOKEN_SECRET` env var (fallback to `ENCRYPTION_KEY` if not set, to avoid requiring new config).

### Endpoints

#### `POST /broker/token`

**Request:**
```
Headers:
  x-api-key: <game-client-api-key>

Body:
{
  "project_id": "string",
  "scopes": ["llm"],  // optional, defaults to ["llm"]
  "ttl_seconds": 900  // optional, default 900 (15min), max 3600 (1hr)
}
```

**Response (200):**
```json
{
  "token": "base64url-encoded-signed-token",
  "expires_at": "2026-09-05T12:34:56.789Z",
  "scopes": ["llm"]
}
```

**Errors:**
- 400 VALIDATION_FAILED - missing/invalid project_id, scopes, or ttl_seconds
- 401 UNAUTHORIZED - missing/wrong x-api-key, or project has no keys configured (FAIL CLOSED)
- 404 NOT_FOUND - project does not exist
- 500 INTERNAL - server error

**Security:**
- Use `verifyGameClientKey` from `src/session/manager.ts:127` (constant-time comparison)
- Check BOTH `settings.game_client_api_key_hash` (legacy) AND `settings.game_client_api_keys[]` (named)
- FAIL CLOSED: if project has no game-client key configured, reject with 401 (do NOT copy session.ts:74 opt-in behavior)

#### `POST /broker/llm`

**Request:**
```
Headers:
  Authorization: Bearer <broker-token>

Body:
{
  "system_prompt": "string",
  "messages": [{ "role": "user"|"model", "content": "string" }],
  "tools": [ ... ],  // optional
  "stream": false    // optional, default false (streaming deferred)
}
```

**Response (200):**
```json
{
  "text": "completion text",
  "tool_calls": [ ... ],  // if any
  "usage": {
    "input_tokens": 123,
    "output_tokens": 456
  }
}
```

**Errors:**
- 400 VALIDATION_FAILED - invalid request body
- 401 UNAUTHORIZED - missing/invalid broker token
- 403 FORBIDDEN - token lacks `llm` scope
- 404 NOT_FOUND - project not found
- 429 RATE_LIMITED - per-token quota exceeded
- 503 LLM_NOT_CONFIGURED - project has no LLM key
- 500 INTERNAL - server error

**Security:**
- Provider key MUST NEVER appear in response or logs
- Rate limit keyed on token ID (not IP, not player) to prevent abuse even if token is scraped

### Rate Limiting

- Reuse `src/security/rate-limiter.ts` with `principal` parameter set to broker token ID
- Default: 10 requests/minute per token (uses existing config.security.rateLimitPerMinute)
- Returns 429 with standard envelope when exceeded

### Token Verification

`requireBrokerToken(requiredScopes?: string[])` middleware:
- Extract `Authorization: Bearer <token>` header
- Verify HMAC signature (constant-time)
- Check expiry
- Check scopes (if required)
- Fail closed on every error path (401/403)
- Attach `{ tokenId, projectId, scopes }` to Hono context

## Test Plan

### Unit Tests (`tests/unit/broker-token.test.ts`)

- Token round-trip (mint → verify → success)
- Reject tampered signature
- Reject expired token
- Reject missing scope
- TTL capped at 1 hour
- Default TTL is 15 minutes

### E2E Tests (`tests/e2e/broker.test.ts`)

**Token minting:**
- 401 with no x-api-key
- 401 with wrong key
- 401 when project has no keys configured (fail-closed)
- 200 with valid legacy key
- 200 with valid named key
- 400 with TTL > 1 hour

**LLM proxy:**
- 401 with no token
- 401 with expired token
- 403 with wrong scope
- 429 when quota exceeded
- 503 when project has no LLM key
- 200 on happy path (mocked LLM provider)

## Implementation Notes

- Mount routes in `src/index.ts` via `buildApiRoutes` (study pattern around line 90-120)
- Routes are mounted once and served at both `/api/v1/broker/*` and `/api/broker/*`
- Use existing error envelope from `src/http/envelope.ts`
- Use existing storage layer to load project/settings/keys
- Use existing LLM factory (`src/providers/llm/factory.ts`) for proxy calls
- No hardcoded secrets - source from env via `src/config.ts` pattern
- No emojis anywhere
- Comprehensive error logging with context
