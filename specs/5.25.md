# 5.25 — Choose storage by deployment, not by whether a user is present

Backlog row: [`backlog.md`](../backlog.md). Fixes ERR-029 in [`ERRORS.md`](../ERRORS.md).

## Problem

Two functions decide which storage backend a request uses, and they are the same
function written twice:

- `getStorage` in [`src/storage/factory.ts`](../src/storage/factory.ts), used by routes
- `getStorageForUser` in [`src/storage/hybrid.ts`](../src/storage/hybrid.ts), used by `src/session/manager.ts`

Both read `userId` and fall back to local file storage when it is null. On Cloud
Run the application filesystem is read-only, so those requests fail:

```
GET /api/v1/projects -> 500
{"error":"Failed to list projects",
 "details":"Failed to list projects: EACCES: permission denied, mkdir 'data/projects'"}
```

The anonymous studio visitor is the small half of this. **A game client carries no
user id** — it authenticates with a project API key — so start-session, converse
and end-session all select local storage in production. The core runtime path
cannot work in the cloud at all.

If the filesystem were writable it would be worse than an error: the service
would quietly read and write container-local data that disappears on the next
deploy, while `/api/health` reported `"storage":"supabase"`.

## The trap

The obvious fix — "when Supabase is configured, always use Supabase" — leaks
every tenant's data. `listProjects` in
[`src/storage/supabase/projects.ts:246`](../src/storage/supabase/projects.ts)
filters by `user_id` **only when a userId is passed**, and the client is the
service-role client, which bypasses RLS. So an anonymous
`GET /api/v1/projects` would return every project belonging to every user.

Backend selection and access control are therefore two separate fixes, and doing
only the first turns a 500 into a data breach.

## Decisions

**D1 — the backend follows the deployment, not the caller.** In a Supabase-backed
deployment (`NODE_ENV=production` and Supabase configured), local file storage is
unreachable. `userId` still decides *what rows* a caller sees; it stops deciding
*which database* is consulted. That is what unblocks the game client, whose
principal is a project API key.

**D2 — the local dev identity keeps its local storage.** `isDevUserId` exists so a
locally signed-in developer never depends on Supabase, and that stays true
regardless of deployment mode. It is checked first.

**D3 — one selector, not two.** `hybrid.ts` is deleted and `session/manager.ts`
imports from `factory.ts`. Two copies of a decision this consequential is the
same shape of bug as the drifted turn loop in 5.19: they were already identical,
and the next edit would have moved only one.

**D4 — the collection routes require a user.** `GET /projects` and
`POST /projects` cannot be ownership-checked, because there is no project yet.
When auth is enabled they now return 401 `UNAUTHORIZED` for an anonymous caller
rather than listing or creating anything. Every `/projects/:projectId` route is
already covered — `verifyProjectOwnership`
([`src/middleware/ownership.ts:48`](../src/middleware/ownership.ts)) denies a null
user whenever auth is enabled.

**D5 — stop returning raw exception text.** The 500 above leaked
`EACCES: permission denied, mkdir 'data/projects'` to an unauthenticated caller.
[`src/http/envelope.ts:49`](../src/http/envelope.ts) already states the rule:
messages must not carry raw exception text in production. The projects routes are
brought in line.

## Scope

Changed: `src/storage/factory.ts`, `src/session/manager.ts`, `src/routes/projects.ts`.
Deleted: `src/storage/hybrid.ts`.
Unchanged: every storage implementation, and the meaning of `userId` as a filter.

## Test plan

`tests/regression/err-029-cloud-storage-selection.test.ts`. Environment is read at
module load, so each case re-imports the module under stubbed env.

1. **Cloud, no user** — `NODE_ENV=production` + Supabase configured, `getStorage(null)`
   returns the Supabase backend. This is the game client, and the assertion that
   fails before the fix.
2. **Cloud, dev identity** — a `isDevUserId` id still gets local storage.
3. **Local dev** — no Supabase configured, any caller gets local storage.
4. **Dev machine with a cloud user** — Supabase configured but not production; a
   real userId gets Supabase, an anonymous caller gets local.
5. **One selector** — `src/storage/hybrid.ts` no longer exists, and nothing
   imports it.
6. **No unscoped listing** — `GET /projects` with auth enabled and no user returns
   401, and never reaches storage.
