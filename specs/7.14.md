# 7.14 — The voice pipeline runs the shared turn and streams it to TTS

Backlog row: 7.14 in [`backlog.md`](../backlog.md), Tier 7. Closes the loop-convergence debt
recorded in 5.13/5.19/5.21. Depends on the `CognitionRuntime` seam (7.5 Phase A).

## Problem

[`src/voice/pipeline.ts`](../src/voice/pipeline.ts) runs its own copy of the conversation turn.
`processTurn` (`pipeline.ts:884-1260`) assembles the prompt, keeps its own `deferredMindContext`
instance variable, starts `runMindAgentLoop` with a hard 8000 ms cap (`pipeline.ts:~932`), streams
the Speaker into `SentenceDetector` and TTS, adds messages to the session, handles `exit_convo`,
runs the follow-up leg with its own TTS pass, and writes the session log (`pipeline.ts:~1170`).
`processTranscript` (`pipeline.ts:764-827`) sanitizes and moderates before that, as the host does again.

Every fix that lands in the host — ERR-030's prompt sections, 7.1's ttft and cache reporting, 7.3's
prefix split, the runtime seam and the single-call runtime — reaches voice only if someone ports it
by hand. The single-call runtime's whole point was first-sentence latency reaching first audio; today
voice cannot select it at all, because `processTurn` never consults `cognition_runtime`.

## Decisions

1. **The host streams.** `RunTurnOptions` gains `onEvent?: (event: CognitionEvent) => void`. The host
   invokes it for every runtime event **as it arrives**, before it consumes the event itself, so a
   caller sees `text` and `follow_up` deltas while generation is still running. `runConversationTurn`
   keeps its signature and return value; text callers ignore `onEvent`.
2. **The host knows it is a voice turn.** Prompt assembly (`turn.ts:254-261`) passes
   `{ voiceMode: state.mode.output === 'voice' }` instead of `{}`. Text sessions are unaffected.
3. **`processTurn` becomes a thin adapter over `runConversationTurn`:**
   - `channel: 'voice'`, `fallbackProvider: this.llmProvider`, no `providers` override (project
     provider resolution applies, as it does for HTTP).
   - `onEvent`: `text` deltas -> `events.onTextChunk` and `SentenceDetector.addChunk` -> `synthesizeSentence`
     per completed sentence; `follow_up` deltas the same way (flush the detector between the two so a
     follow-up never glues to the primary's last sentence); `tool_call` -> `events.onToolCall`;
     `tool_result` -> `events.onMindActivity` with the same payload shape it emits today.
   - After the promise resolves: flush the detector and TTS, emit `onExitConvo` from
     `result.exitConvoResult` (with the cooldown the pipeline computes today), `onGenerationEnd`.
   - Remove from the pipeline: prompt assembly, `deferredMindContext` (the host reads and writes
     `state.deferred_mind_context`), the Mind loop and its 8000 ms constant, `addMessageToSession`
     for assistant/follow-up messages, `handleExitConvo`, the follow-up leg, `appendSessionLog`,
     `updateSessionInstance`/mood blending. Each of these now happens once, in the host.
   - Keep in the pipeline: transcript aggregation, `runSecurityPipeline` **only for rate limiting**
     (drop its sanitize and moderate calls — the host does both and records them on the result;
     surface `result.moderationAction === 'exit'` through the same `onExitConvo` path), the STT/TTS
     sessions, `LatencyTracker` marks (`firstToken` on the first `text` event, `firstAudio` unchanged),
     `wasExitConvoUsed()` (from `result.exitConvoResult`), `resetTranscriptState`.
4. **Behaviour changes, stated:** the voice Mind budget becomes the project's `mind_timeout_ms`
   (default 15 s) instead of a fixed 8 s; the voice turn is logged by the host (once) with the
   host's field set, which is a superset of what the pipeline wrote; voice sessions can now run
   `cognition_runtime: 'single'`. Record all three in the report.
5. **Not this item:** barge-in, TTS send ordering and Cartesia continuation (7.17), a whole-turn
   budget, streaming `stripNarration` inside `SentenceDetector` (7.17).

## Scope

Touch: `src/conversation/turn.ts` (`onEvent`, `voiceMode`), `src/voice/pipeline.ts` (`processTurn`,
`processTranscript`, `runSecurityPipeline`, removed members), and the pipeline's imports.

Do not touch: `src/core/runtime/*`, providers, `SentenceDetector`, `ws/handler.ts` beyond what the
pipeline's changed surface forces.

## Test plan

`tests/unit/turn-stream-events.test.ts`:
- With stub providers whose Speaker yields three text chunks, `onEvent` receives the `text` events
  in order **before** `runConversationTurn` resolves (record the timestamps or push into an array and
  assert the array is complete at the moment the `done` event arrives, not only after the promise).
- A turn with an action tool delivers `tool_call`, `tool_result` and `follow_up` events through `onEvent`.
- Omitting `onEvent` changes nothing (existing suites are that proof).
- A session whose `mode.output` is `'voice'` produces a speaker prompt containing the voice-mode
  task text (assert on `result.speakerPrompt`); a text session does not.

`tests/unit/voice-pipeline-shared-turn.test.ts` (follow `tests/unit/voice-latency-config.test.ts`
for constructing a `VoicePipeline` with stub STT/TTS/LLM providers and a scratch project):
- A text input through `handleTextInput` calls `runConversationTurn` once with `channel: 'voice'`
  (spy on the module export) and synthesizes exactly the sentences the stub Speaker produced, in order
  (mock TTS captures `synthesize` calls).
- The session log has exactly one `turn` record for that voice turn (no double write).
- With the project setting `cognition_runtime: 'single'`, the pipeline's turn makes one `streamChat`
  call and the log record's `runtime` is `single`.
- A moderation exit (jailbreak phrase input) reaches `events.onExitConvo`.

Existing suites stay green. Run the stub-mode playground scenarios before and after; text-path
records must be identical minus timings.
